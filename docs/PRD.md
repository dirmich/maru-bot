# 분산 marubot과 사용자별 기억 관리 요구사항

작성일: 2026-10-28

## 목표

사용자가 하나의 marubot 또는 Admin에 요청하면 사용자 소유 장비의 marubot들이 독립 작업을 병렬 실행하고, 의존 작업은 순서대로 수행한다. Admin은 장비 연결·활성 작업·승인·실패·기억 현황과 실행 출처를 한 화면에서 제공한다.

## 사용자 흐름

1. Google SSO로 Admin에 로그인한다. Google sub를 사용자 식별자로 사용한다.
2. 장비를 등록하고 일회 표시되는 장비 자격 자료를 안전한 로컬 환경에 설정한다.
3. worker를 TLS와 로컬 허용 정책으로 실행한다. heartbeat로 버전·능력·자원 상태를 갱신한다.
4. 자연어로 작업을 요청하거나 Admin에서 구조화된 작업 DAG를 작성한다.
5. 실행할 노드·도구·인자를 확인한다. 읽기 이외 작업은 각 작업별 승인 후 실행한다.
6. 진행 이벤트, 결과, 실행 장비와 도구를 조회하고 필요하면 취소한다.
7. 단기 기억을 검토해 장기 Wiki로 승격하고, 검색·수정·삭제·만료를 관리한다.

## 필수 요구사항

- 사용자별 장비·작업·감사·기억·Wiki를 분리하고 모든 접근에서 인증 주체를 사용한다. 요청 본문의 owner 값은 권한 근거로 쓰지 않는다.
- 런타임 Wiki는 backend가 사용자별 저장한다. 개발용 knowledge_base를 런타임과 연결하지 않는다.
- 장기/단기는 보존 정책, private/shared는 같은 사용자 내 공개 범위다. private 기억은 지정 노드·세션에 제한한다.
- 동일 바이너리 worker 역할, HTTPS JSON API와 SSE, Tailscale 사설망, 전송 교체 인터페이스를 제공한다.
- 로컬 도구 정책은 최초 원격 실행부터 fail-closed다. 원격 요청에 의한 재위임을 차단한다.
- 작업·멱등 키·이벤트·승인·실행 결과를 SQLite에 영속 저장한다. 실행 여부 불명 작업을 다른 장비로 자동 재전송하지 않는다.
- 병렬 수·본문 크기·출력 크기·실행 시간·이벤트 조회량을 제한한다.
- Admin은 실제 데이터만 표시한다. 로딩·빈 상태·인증 실패·통신 단절·오프라인을 구분한다.

## 안전성과 완료 기준

- 사용자 A가 B의 장비·Wiki·작업·이벤트에 접근할 수 없음을 통합 테스트한다.
- 두 worker의 동시 실행, DAG 의존성, 정책 거부, 중복 제출, 취소, 재시작 복구, 승인 거부·승인 만료를 테스트한다.
- 테스트용 TLS worker 통신과 SSE 재연결을 검증한다. 실제 원격 장비 배포는 연결 정보가 준비된 후 별도 수행한다.
- Google 자격 자료가 없는 환경은 로그인 불가 상태를 명확히 표시하며 임의 사용자 헤더를 허용하지 않는다.
